# Local vs Online 差距根因审计（READ-ONLY）

**日期**：2026-09-22 · **性质**：纯只读审计。**未训练、未改任何文件、未生成 submission、未读取任何测试集 GT**
（两套测试集目录内 label 类文件数均为 **0**，不存在 GT）
**起因**：初赛 local/online 差 ≈1.3 分，复赛扩大到 ≈8 分

---

## 0. 核心结论（一句话）

> **差距的主体不是"过拟合/泄漏"，而是记账口径**：项目一直引用的 local 56.7 是 **fork 口径**，
> 从来就不是榜单口径。同一批预测换用官方口径即为 **51.66**，一步就吃掉 **−5.03**。
> 余下 **−2.95** 才是真正的 local→online 落差。

## 2. ⚠️ P0-3 序列泄漏：**假设被数据否定**

### 2.1 切分代码确实完全不感知序列

`scripts/train.py:123-147` `_split_by_group`：按 **`_base_stem`（仅剥 `_augN`/`_balN` 后缀）** 分组，
`seed=42` 随机 shuffle 后取前 20% 为 val。**没有任何 sequence / scene / 相机维度。**
文件名含明显序列结构（`shuming_<N>_<frame>`、`AAAAAA_BBB_<frame>`、`hehe_*`、纯数字帧号），
理论上随机切分会把同源相邻帧分到两侧。

### 2.2 用**数据驱动**（不猜文件名）量化

对全部 2000 张训练池图像做 64×64 灰度互相关，按 `r ≥ 0.90` 取连通分量：

| 阈值 | 簇数 | 最大簇 | **跨 train/val 的簇** | 覆盖图像 | **其中 val** |
|---|---:|---:|---:|---:|---:|
| r≥0.95 | 1802 | 37 | 19 | 177 | **39** |
| **r≥0.90** | 1694 | 61 | **34** | 256 | **64** |
| r≥0.80 | 1423 | 236 | 43 | 543 | 125 |

⇒ **400 张 val 中有 64 张（16%）在 train 里存在近重复（r≥0.90）**，cluster-aware 切分可把它降到 0。

### 2.3 但**这不是**8 分差距的原因 —— 三组对照推翻了它

| 集合 | → **训练拆分(1600)** 最近邻 median | r≥0.99 | r≥0.90 |
|---|---:|---:|---:|
| **本地 val (400)** | **0.676** | **6.8%** | 15.8% |
| 初赛 test (1000) | 0.740 | **16.6%** | 27.1% |
| 复赛 test (1000) | 0.727 | **11.6%** | 23.5% |
| *(训练拆分内部最近邻，基线)* | 0.692 | 7.8% | 18.2% |

**三条关键读数**：

1. val→train 的相似度（6.8% @r≥0.99）**低于训练集自身的内部重复率（7.8%）** ——
   随机切分并没有让 val 异常地"像训练数据"。
2. val→train 的相似度**低于两套测试集**（16.6% / 11.6%）。
3. 逐像素 median：val 0.676 < 复赛 0.727 < 初赛 0.740。

> **结论：本地 val 并不比测试集更"容易"。按这个代理指标，test 反而比 val 更接近训练数据。**
> 因此 **"random val 泄漏导致 local 虚高" 这一假设不成立**，不能用来解释 8 分差距。
> 数据集本身确实含 ~16-18% 近重复（同源连拍帧），这是**数据的性质**，随机切分只是把它按比例分到两侧。

## 3. P0-4 初赛 vs 复赛：**无结构域差异**

三套数据（train / 初赛 test / 复赛 test）无标签统计**高度一致**：

| 项 | train | 初赛 test | 复赛 test |
|---|---|---|---|
| 分辨率构成 | 1080×1920 / 360×640 | 同 | 同 |
| visible dtype | uint8 3ch | 同 | 同 |
| infrared dtype | uint8 3ch | 同 | 同 |
| depth dtype | **uint16 1ch**（1080p）/ uint8 3ch（360p） | 同 | 同 |
| 扩展名 | png/jpg 混合 | 同 | 同 |
| **三模态配对完整性** | 2000/2000，缺失 0 | 1000/1000，缺失 0 | 1000/1000，缺失 0 |
| visible 均值 | 113.0 | 114.0 | 114.8 |
| infrared 均值 / 零值率 | 110.4 / 0.070 | 108.8 / 0.090 | 107.8 / 0.102 |
| depth 均值 / 零值率 | 23.0 / 0.325 | 23.4 / 0.353 | 24.5 / 0.325 |

**唯一的显著差异是内容层面的**：初赛 test 与训练数据的近重复率（16.6% @r≥0.99）**高于**复赛（11.6%）——
而两者的线上分排序（55.53 > 47.99/48.71）与之**同向**。

> ⚠️ 这**不能**用于任何 test-set-specific 调参（且本轮不据此设计任何方案）；
> 只作为"两套测试集在内容分布上确有差别"的事实记录。结构层面（格式/尺寸/dtype/配对）**没有**域差异。

## 6. 需要**本地实验**才能确认的（本轮不做）

1. **D2 类计数约定**：若线上某类无 GT，官方是否仍除以 12。唯一可能的大项，本地不可验证，
   建议向主办方确认（或观察一个已知缺类场景）。
2. **A1 的稳定性**：fork→官方口径差随模型低置信长尾而变（F4 时代 −0.0308，D/D' 时代 −0.049/−0.055），
   不是常数 → 不能当固定偏移用。
3. **复赛 test 的难度归因**：需要一份带 GT 的公开验证集或主办方反馈，本地无法定论。

## 7. 是否应继续训练 —— **暂不建议，先把 local proxy 修好**

理由：当前 headline local 指标（fork）与榜单口径相差 ~5 分且**符号可能翻转**
（本项目已记录 fork 与官方口径多次反向）。在此 proxy 上继续做模型选择，
等于**在错误的量尺上优化**。建议顺序：

```text
① 把判据换成「官方口径」（official_map.py 的官方行），fork 仅作训练内参考曲线
② 给 100 框上限加自动闸门（B1）
③ 每次评测前确认 cap=100 已生效（D1）
④ 之后再谈训练
```

## 8. 建议的 sequence-aware 验证方案（**本轮不实施**）

不改现有 split，**新增**一套只读的评测切分用于诊断：

```text
1. 数据驱动建组（不依赖文件名猜测）：
   对训练池 2000 张做 64×64 灰度相关，取 r≥0.90 的连通分量作为 group
   （实测：1694 组，最大组 61 张，34 组跨 train/val，覆盖 64 张 val）
2. 按 group 重新 80/20 切分（group 不跨侧），得到 group-val
3. 用**官方口径**在 group-val 上评当前模型，与 random-val 的官方口径对比
4. 两者之差 = 「同源泄漏带来的虚高」的**实测量**（而不是猜）
```

**预期**：由 §2.3，random-val 与 group-val 的差异可能很小（因为 val 本就不比 train 内部更像），
所以这一步更可能是**排除**泄漏、把注意力集中到口径问题上——这正是本审计已经指向的方向。
